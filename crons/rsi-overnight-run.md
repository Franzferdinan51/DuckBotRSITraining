WINDOW AND GUARDRAILS
- Runs only while Duckets is asleep: window 01:00–10:00 ET. Training must be DONE by 10:00 AM: any training still running at 09:45 gets stopped (checkpoints are kept) — no exceptions. Eval, deployment, and the morning report wrap inside the same window whenever possible.

LIFELINES ARE NEVER TOUCHED: Muse.app, LM Studio itself, Terminal, SSH, Tailscale, the Hermes gateway, AVG, and all system processes stay up — unloading a model is fine, killing a lifeline never is. (5) If headroom still isn't genuinely there after cleanup, the night is a prep night — never force a run onto a loaded machine.

VERSION LINEAGE (build on every run)
- Each model has a lineage ledger at ~/workspace/goals/rsi-overnight-small-model-training-program/hidden_files/lineage-<model>.md. Read it before planning or running: tonight's run trains FROM the latest verified version (<model>-rsi-v<n>; the base model for v1), never from scratch, so improvement compounds. The parent ARTIFACT is that version's bf16 merged master.
- A candidate becomes v<n+1> only if it beats its PARENT at the eval gate BY THE PRE-SET MARGIN (≥2× the paired SE of the difference — research amendment: a bare "beats parent" at our eval sizes is a noise ratchet; ties keep the parent; a sub-margin win gets ONE seed-repeat and the repeat decides). A regression is discarded, the chain stays at v<n>, and the next run retries from v<n> — never build on a regression.
- Label versions everywhere by their lineage name <model>-rsi-v<n> (LM Studio install name, reports, ledger). Dates/parentage/dataset live in the ledger.
- FRESH CHALLENGER — the anti-degradation control (Duckets, 2026-10-22; his standing worry is gradual loss of general skills over time): no chain compounds forever on faith. Triggers (any one): two consecutive gate losses on the chain; cumulative drift vs base reaching HALF the lineage's drift floors; every 4th kept version. A triggered challenger is a planned sequence (written run plan with a PRE-DECLARED token/epoch budget): train FRESH from the BASE on the chain's accumulated curated data (all chunks, replay included), then face the chain head at the FULL gate judged on the CONFIRMATION set (target eval + frozen suite + battery, in-window or via the next benchmark night). Winner becomes the chain's current version (a winning challenger logs as a fresh-restart version); loser is discarded with numbers. Record the face-off in the lineage ledger + morning report either way — it's the program's running evidence on whether compounding still helps that model. The drift floors remain the hard stop; the challenger is the early, empirical check.

EVAL GATE AND DEPLOYMENT
- ARTIFACT TRUTH (research amendment): score THREE artifacts — the adapter, the bf16-merged model, and the SERVING artifact (quantized, production template/settings) — and the GATE JUDGES THE SERVING ARTIFACT. All evals run through the production serving configuration. The bf16 merged master of a kept version is retained as the lineage parent; quantized copies are derived from it, never the reverse.
- After a real run: evaluate parent vs candidate on the held-out SELECTION set, using the metric named in the run plan. Keep the candidate only if it beats the PARENT BY THE PRE-SET MARGIN (≥2× paired SE); ties keep the parent; sub-margin wins get one seed-repeat. Otherwise discard it and log the loss with the reason (the chain does not advance). At most 3 pre-declared checkpoints are evaluated. Record loss curve endpoints and eval numbers — real numbers, no rounding into a win. The CONFIRMATION set is touched only at milestones and challenger face-offs.
- ANTI-LOBOTOMY GUARD (Duckets, 2026-10-22; research-amended): the target eval is only the FIRST test. Every candidate ALSO takes the frozen regression suite — a fixed general-capability set (instruction following, reasoning, coding, tool use, conversation, SAFETY/refusal + over-refusal, per-chunk probes, + the failure-ledger eval cases) stored under /Volumes/Sabrent/datasets/rsi/frozen-suite/ on the Mac; it is NEVER trained on and NEVER edited to make a run pass — scored vs PARENT and vs BASE v0, per domain, plus drift signals (general-text PPL, output length, distinct-n, refusal rate). Winning the target eval while regressing on the frozen suite = discard, exactly like a gate loss: versions train on top of versions here, and small general losses per generation compound into a lobotomized model. If the frozen suite does not exist yet, building it (held-out general material + failure eval cases, curated + backed up like any dataset, with baseline scores recorded for the base and the current version) is prep-night work that outranks a real run for any lineage past v1 — never advance a chain to v2 or beyond without frozen-suite scores on record. Record parent/base/candidate frozen-suite scores in the lineage ledger after EVERY run, pass or fail. Any clear regression on any frozen domain vs parent fails the candidate; breaching any PER-DOMAIN drift floor vs base stops the chain — the next run restarts from base or the last known-good version, and drifted versions are never deployed.
- BENCHMARKS (evidence layer + milestone veto, PROGRAM.md Benchmarks section — battery v3): every kept version gets benchmark records on non-training nights via rsi-benchmark-nights (Mon/Wed/Fri/Sun); inside this window, run benchmarks only if time genuinely allows after eval + deployment + verification, otherwise flag for the benchmark job and say so in the report. Battery v3 leads with IFEval/GSM8K/ARC-C/MMLU-canary (GPQA is evidence-tier at this scale; TruthfulQA is not a gate; vision gate is MMBench/SEED + POPE). At chain milestones (every 4th kept version, challenger face-offs), FULL MMLU / BFCL-full / safety runs carry a pre-declared VETO — below the lineage's recorded floor blocks deployment pending Duckets' review. Benchmark items are eval-only, never training data.
- If kept: merge/fuse the adapter INTO THE BF16 MASTER and install the derived serving copy into the LM Studio library on the Mac under its lineage name <model>-rsi-v<n+1>. Then VERIFY IN LM STUDIO ITSELF: load it via lms, run real prompts including the eval prompts, and an image test for vision models; compare quality against the parent.
