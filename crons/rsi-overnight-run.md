- **Schedule:** weekly Tue/Thu/Sat 01:00, timezone America/New_York
- **Owner:** goal `rsi-overnight-small-model-training-program`
- **Delivery:** the run's morning report goes to the chat that created the job
- **Body:** the full driver instructions below (this is the saved job body as of 2026-10-22, after the audit fixes)

---

RSI OVERNIGHT RUN — execute the program in docs/RSI-PROGRAM.md (read it first, every run; the Mac copy lives next to the training install). The owner authorized this standing program on 2026-10-22; start_training inside it is pre-authorized ONLY under the gates below. Standing emphasis: every real run must be a PROPER run prepared in advance for actual improvement — the details matter; an improvised or underprepared run is worse than a prep night.

WINDOW AND GUARDRAILS
- Runs only while the owner is asleep: window 01:00–10:00 ET. Training must be DONE by 10:00 AM: any training still running at 09:45 gets stopped (checkpoints are kept) — no exceptions. Eval, deployment, and the morning report wrap inside the same window whenever possible.
- Nothing over 35B is ever trained. Roster: Gemma 4 12B / E4B / E2B, Ornith 1.5 9B, MiniCPM-V 4.7 1B. The 27B–35B tier is frozen (teachers/judges only).
- Prefer QAT-style runs (LoRA against the quantized base) where the tooling supports it and it helps the target's shipped form.
- PREFLIGHT + RAM PREP (standing order — manage RAM and load before EVERY run; this is what training mode is for): (1) Measure honestly — `lms ps` + real RSS totals (never memory_pressure free %; it counts purgeable cache and has lied before). (2) Wait for quiet — if a Hermes brain job or anything else is actively GENERATING, wait and re-check every 15 min until quiet or 04:00, whichever first; still busy at 04:00 = prep night. (3) No other training run live on either engine. (4) Once quiet, FREE THE MACHINE training-mode-style: unload loaded LM Studio models that tonight's run and tonight's remaining scheduled jobs don't need (`lms unload`), and clear non-essential user apps/processes per the training-mode discipline. LIFELINES ARE NEVER TOUCHED: the assistant app, LM Studio itself, Terminal, SSH, Tailscale, the Hermes gateway, the antivirus, and all system processes stay up — unloading a model is fine, killing a lifeline never is. (5) If headroom still isn't genuinely there after cleanup, the night is a prep night — never force a run onto a loaded machine.

ENGINES — use both, per job (the run plan names the engine and why)
- mlx-lm-lora (MCP): the RSI driver for TEXT work. Drive it with the tested one-shot driver (`tools/rsi_mcp.py`), in a FOREGROUND remote-shell call, one driver at a time. Tools: list_training_modes, check_training_config, start_training, training_status, training_log, list_training_runs, stop_training. A bare start_training return is NOT proof of training — confirm via training_status + training_log lines. check_training_config must pass before any start_training.
- Unsloth (Studio on the Mac): trains VISION (image+text jobs, e.g. CannaAI photo diagnostics) and any job where it is plainly the better tool. Drive it with the unsloth-manager skill's tooling and Bolt-era discipline: guarded launcher scripts (`if __name__ == "__main__"`), verify by training_progress/log lines — never by a route return or DB status alone, stage payloads in durable folders never only /tmp. Unsloth-the-tool does NOT un-park Bolt: Bolt itself is never a target under this program.
- An engine route not yet proven for tonight's target = prep/smoke night that proves it (config validation + tiny run), never a hopeful full run. The 09:45 stop rule binds both engines.

VERSION LINEAGE (build on every run)
- Each model has a lineage ledger (`lineage-<model>.md`, see templates/). Read it before planning or running: tonight's run trains FROM the latest verified version (`<model>-rsi-v<n>`; the base model for v1), never from scratch, so improvement compounds.
- A candidate becomes v<n+1> only if it beats its PARENT at the eval gate. A regression is discarded, the chain stays at v<n>, and the next run retries from v<n> — never build on a regression.
- Label versions everywhere by their lineage name `<model>-rsi-v<n>` (LM Studio install name, reports, ledger). Dates/parentage/dataset live in the ledger.

FAILURE + SUCCESS MINING (experience-driven improvement — pull from the whole fleet, not just the datasets)
- The experience ledgers live on the Mac: `~/mlx-lm-lora/failures.jsonl` AND `~/mlx-lm-lora/successes.jsonl`. BOTH agents feed them: Hermes appends failures and VERIFIED successes as he sees them; the driver appends from chat; the owner's corrections count as failures; every gate pass / verified deployment is recorded as a model success. Only verified outcomes are success entries — include the proof (how it was checked on the thing itself).
- On prep nights — and during every target's curation — distill new FAILURE entries into (a) held-out EVAL cases for that target (never trained on) and (b) corrected-behavior training rows, and new SUCCESS entries into (c) positive training rows (verified-good behavior worth reinforcing) and operator-corpus material. Success rows are TRAIN-side only, never eval — eval stays hard (failure cases + frozen suite), never the highlight reel. Eval sets for a target must include its failure-derived cases once any exist.
- Experience steers the program: failure categories steer chunk priority and curation coverage (fixing real weaknesses outranks generic volume); success patterns steer what gets reinforced. The morning report names which failure categories the night targeted, whether the failure eval cases moved, and which verified successes were distilled into tonight's data.

TONIGHT'S TARGET, THE RUN PLAN, CURATION, AND BACKUP GATES
- Rotation state lives in `rotation.md` (see state/ and templates/) — read it, take the next target, update it when the night ends. THE MAIN TRACK is actual improvement on everything: the fleet's real work across the board (agent work, coding, decisions, tool use), fed by the code/decision corpora AND the failure ledger — most nights belong to it. Specific tracks are rotation slots inside that aim: cannabis/CannaAI is ONE track (MiniCPM-V 4.7 1B — text via mlx-lm-lora, photo diagnostics via Unsloth vision once a labeled photo set exists; Ornith 9B alternate; the own-grow diagnostics set is TO BUILD — a prep task, never invented data) — never let a specific track headline the program or crowd out main-track nights. The RSI operator track (PLANNED) takes a slot only after its corpus prep night lands.
- SMOKE NIGHT (one-off, scheduled separately for the program's first run, Ornith 1.5 9B): pipeline proof (validate → train a few steps → status → log → stop) + MEASURED real steps/sec throughput — every later run plan's chunk math uses that measurement, never a guess. No eval gate, no deployment on a smoke night; report pipeline health only. On RECURRING nights the smoke is history: find its measured throughput in the run record and use it; do NOT re-run a smoke in place of tonight's scheduled prep or real work. Only if no smoke result exists anywhere in the record does a recurring night become a smoke night — and the report says why.
- RUN PLAN (mandatory for every real run): a real run executes a written plan (`run-plans/<date>-<target>.md`, see templates/run-plan-template.md) naming: target model + job; the ENGINE (mlx-lm-lora or Unsloth) and why; the PARENT VERSION it builds on; the exact curated dataset version (backup path) and, for large source material, WHICH CHUNK this run covers (chunk k of m) with the remaining chunks' place in the rotation; training mode/type; key hyperparameters; a step budget WITH throughput math (from measured throughput) showing training finishes well inside the window (target ≤ ~7h of training so eval/deploy/report fit before 10 AM); the eval set + the metric that decides keep/discard (candidate vs PARENT; eval includes failure-derived cases where they exist); and the deployment name `<model>-rsi-v<n+1>`. If tonight's target has no complete run plan when the window opens, tonight is a PREP night: do the curation + backup + config validation + failure distillation and WRITE the plan, then report it ready for the next run night. Never improvise a real run at 1 AM.
- SIZING / CHUNKING: size every run to fit the window — never launch a run whose budget only works if nothing goes wrong. Big datasets are split into sequential chunks across nights (chunk 1 → v1, chunk 2 trains v1 → v2, ...); each chunk is curated and backed up as its own dataset version, and faces the eval gate before the chain builds on it. A 68K-row corpus is MANY nights of chunks, never one run.
- SOURCES — four families, one pipeline: (1) the owner's existing corpora (the backed-up Unsloth-side sets, the merged corpus, domain corpora); (2) FLEET EXPERIENCE — the failure + success ledgers distilled from both agents' work (see above); (3) PUBLIC HUGGING FACE DATASETS staged under `<datasets>/hf/` (the fleet already holds OpenHermes-2.5, glaive-function-calling-v2, SlimOrca, s1K, Pasta009 and others) — license checked + repo id/revision recorded in the manifest, quality-filtered hard, privacy screen applied anyway (public sets carry PII too), sample-inspected before full curation, downloads overnight only, and NEVER re-upload someone else's dataset or a derivative passed off as original; (4) teacher-generated material from the frozen 27–35B tier. Everything enters training only through curation + an RSI-tree backup (below).
- CURATION (mandatory before training, per the program doc; use `tools/curate_dataset.py`): clean the set (drop malformed/empty/degenerate rows and near-duplicates, fix chat format), filter for quality, balance sources, and hold out the eval set FIRST — never train on eval rows. Produce a manifest (sources, row counts before/after, what was filtered and why, date) and version the set.
- PRIVACY SCREEN (mandatory): no private/personal information enters ANY set — train, eval, frozen suite, or failure rows. Barred: personal identifiers (real names beyond public handles, emails, phones, addresses, DOB), family and personal-life content, private messages/conversations as content, financial/trading account details, identifying site specifics, and all credentials, tokens, keys, local machine paths, and LAN/tailnet addresses. Scrub a row if it stays useful scrubbed, drop it otherwise; the manifest records screened/scrubbed/dropped counts, and a set with an unrecorded screen does NOT train. Two reasons: these models and datasets are shareable artifacts (the owner publishes model ports publicly — personal data in training data means a share/upload compromises him, and a trained model can regurgitate memorized personal data), and personal specifics are noise that hurts general quality. Sources are screened at curation every time — no set inherits a "probably clean" from its corpus. Session-history corpora (the operator track) are mined for decisions and corrected behavior with personal content stripped; failure-ledger entries record behavior, never personal payloads verbatim. TOOL STATE (updated 2026-10-22 late): `curate_dataset.py`'s `privacy_screen()` IS wired into its main flow (the co-agent wired it after the audit; the manifest carries `stats.privacy_screen` screened/scrubbed/dropped counts; synthetic-tested — PII scrubbed, clean rows intact). The driver's remaining duty is the v2 lesson: after ANY curation, eyeball the manifest counts against the source before training — a buggy first wiring once dropped 584/585 rows and the corrupt set got backed up before anyone looked (marked SUPERSEDED in-folder; the failure ledger has the entry).
- BACKUP (mandatory, before training; use `tools/backup_dataset.py`): copy the curated train set + held-out eval set + manifest to `<datasets>/rsi/<target>/<date>-v<n>/` on the external drive (new version folder each time, never overwrite; RSI datasets live ONLY under `datasets/rsi/` — never mixed with the Unsloth-side datasets). Verify the copy (file sizes / row counts). Train from the backed-up copy. If the backup cannot be completed or verified, the run does NOT start — report it as a blocked night.
- After plan + curation + backup + passed config validation, start the run per the plan on its named engine; poll status/log; enforce the 09:45 stop rule.

EVAL GATE AND DEPLOYMENT
- After a real run: evaluate parent vs candidate on the held-out eval set, using the metric named in the run plan. Keep the candidate only if it beats the PARENT; otherwise discard it and log the loss with the reason (the chain does not advance). Record loss curve endpoints and eval numbers — real numbers, no rounding into a win.
- ANTI-LOBOTOMY GUARD: the target eval is only the FIRST test. Every candidate ALSO takes the frozen regression suite — a fixed general-capability set (instruction following, reasoning, coding, tool use, conversation + the failure-ledger eval cases) stored under `<datasets>/rsi/frozen-suite/`; it is NEVER trained on and NEVER edited to make a run pass — scored vs PARENT and vs BASE v0. Winning the target eval while regressing on the frozen suite = discard, exactly like a gate loss: versions train on top of versions here, and small general losses per generation compound into a lobotomized model. If the frozen suite does not exist yet, building it (held-out general material + failure eval cases, curated + backed up like any dataset, with baseline scores recorded for the base and the current version) is prep-night work that outranks a real run for any lineage past v1 — never advance a chain to v2 or beyond without frozen-suite scores on record. Record parent/base/candidate frozen-suite scores in the lineage ledger after EVERY run, pass or fail. Any clear regression on any frozen category vs parent fails the candidate; cumulative drift vs base crossing the lineage's pre-set ledger line stops the chain — the next run restarts from base or the last known-good version, and drifted versions are never deployed.
- BENCHMARKS (evidence layer, docs/RSI-PROGRAM.md Benchmarks section): every kept version gets a GPQA Diamond record (battery v1, the fleet's tested harness) — run it inside this window only if time genuinely allows after eval + deployment + verification; otherwise flag it for the next benchmark-night job (Mon/Wed/Fri/Sun) and say so in the report. Benchmarks are reported next to the parent/base records and run mostly on non-training nights as preparation. A headline-benchmark crater vs parent is a keep/remove review trigger — report it prominently; never act on it unilaterally mid-night. Benchmark items are eval-only, never training data.
- If kept: merge/fuse the adapter and install the result into the LM Studio library under its lineage name `<model>-rsi-v<n+1>`. Then VERIFY IN LM STUDIO ITSELF: load it, run real prompts including the eval prompts, and an image test for vision models; compare quality against the parent.
- SWAP RULE (exact): only after the new version verifies working in LM Studio, remove the PREVIOUS RSI version of that same model from the library by moving it to the archive (`lmstudio-archive/` on the external drive) — never hard-delete, never remove the original base model. A FAILED test never costs the old working model: if verification fails, pull the new model, leave the old one untouched, and report the failure plainly. Do deployment only while LM Studio is quiet (same preflight discipline — never unload a model a live session is using).
- LEDGER: update `lineage-<model>.md` with the outcome (new current version or discarded attempt, dataset version + chunk, engine, steps, eval vs parent, frozen-suite scores + cumulative drift vs base, dates) before filing the report.

DELIVERY
- File a concise morning report as this run's result: what ran or why it didn't (smoke / real run per plan / prep night / blocked), the engine used, the pre-run RAM state (what was loaded, what was unloaded/cleared, headroom at start), the lineage move (v<n> → v<n+1> or chain held), dataset size before/after curation + chunk info, which failure categories were targeted and how the failure eval cases moved, the backup path, eval verdict vs parent, the frozen-suite verdict + cumulative drift vs base, benchmark score vs parent/base records (or that it's queued for a benchmark night), deployment outcome (installed name, verification result, old version swapped or why not), blockers, next rotation target. Also append one activity entry to the program's tracked item with the same outcome, and write the run's raw notes to the bookkeeping folder (not the user-facing files).
