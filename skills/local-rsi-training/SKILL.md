# Local RSI Training — the overnight small-model improvement loop

Use when: running, prepping, debugging, or reporting an RSI overnight run; curating or backing up a training dataset; deploying a trained adapter into LM Studio; or answering anything about the program's rules. Canonical program doc: `~/workspace/goals/rsi-overnight-small-model-training-program/files/RSI-PROGRAM.md` (Mac copy: `~/mlx-lm-lora/PROGRAM.md`) — read it before acting; this skill is the how, that doc is the law.

## The program in one paragraph
Tue/Thu/Sat, 1:00–10:00 AM ET (training DONE by 10 AM; 09:45 = stop_training), only while Duckets sleeps. One model + one job per night. Every real run executes a written run plan (goal workspace `hidden_files/run-plans/<date>-<target>.md`) prepared in advance — no plan, no run; the night becomes prep that writes the plan. Nothing over 35B is ever trained. Roster: MiniCPM-V 4.7 1B, Gemma 4 E2B/E4B/12B, Ornith 1.5 9B; 27–35B tier is frozen teachers/judges (sole exception: a deliberate coding run Duckets approves separately). **Two engines, chosen per job in the plan:** mlx-lm-lora (text RSI loop) and Unsloth (vision training + any job where it's plainly better) — identical gates on both; Unsloth-the-tool does not un-park Bolt. QAT-style (LoRA on the quantized base) preferred where it helps. Driver cron: `rsi-overnight-run` (Juno side). Hermes has the same orders in its own skill + memory: never start_training outside the program, its 3 AM brain jobs have right of way, and it stops any out-of-window run.

## Pipeline (fixed order, no skipped steps)
0. **Run plan** — a real run needs `run-plans/<date>-<target>.md` (target+job, **parent version** from the lineage ledger, dataset version/Sabrent path + chunk k of m if the material is large, mode, hyperparams, step budget with throughput math proving it fits the window, eval metric vs parent, deploy name `<model>-rsi-v<n+1>`). Missing or incomplete → prep night that finishes it.
1. **Preflight + RAM prep** — `lms ps` quiet (nothing GENERATING; wait/re-check to 04:00 max, then prep night), no other training run live, RAM headroom real (RSS, never memory_pressure free %). Once quiet, FREE THE MACHINE training-mode-style (Duckets' standing order): unload loaded models tonight doesn't need, clear non-essential apps/processes — lifelines (Muse.app, LM Studio, Terminal, SSH/Tailscale, Hermes gateway, AVG, system) never touched. Still short after cleanup → prep night; never force a run onto a loaded machine.
2. **Curate** — `tools/curate_dataset.py RAW.jsonl OUTDIR` (drops malformed/empty/too-short, exact + near dupes; eval split held out FIRST, never trained on; writes manifest.json with counts). **Research amendments (2026-10-22, PROGRAM.md is the law):** every source is DECONTAMINATED against all eval/frozen/benchmark items (n-gram + embedding top-k — rephrased contamination evades n-grams; rate in the manifest, flagged rows dropped); chunks of a big source are STRATIFIED INTERLEAVES of the whole, never topical blocks; replay = ~5–8% general + ~10–20% stratified replay of ALL prior chunks of the chain; per-row cumulative exposure tracked (retire >~4); synthetic share capped (≤50% default, real rows never shrink generation-over-generation, per-row provenance source/teacher/verifier, "verified" needs a verifier independent of the generator). **Privacy screen (mandatory, Duckets 2026-10-22):** NO private/personal information in ANY set — train, eval, frozen suite, failure rows. Barred: identifiers (real names beyond public handles, email, phone, address, DOB), family/personal-life content, private messages as content, financial/account details, credentials/tokens/keys, local paths, LAN/tailnet addresses. Scrub a row if it stays useful scrubbed, drop it otherwise; the manifest records screened/scrubbed/dropped counts. Why: these models and datasets are shareable artifacts (he publishes to HF — personal data in training data means a share/upload compromises him, and a model can regurgitate memorized personal data), and personal specifics are noise that hurts general quality. Session-history corpora (operator track) are mined for decisions, personal content stripped. If the curated set isn't worth training on, the night is a prep night. **Experience mining rides along (failures AND successes, whole fleet):** distill `~/mlx-lm-lora/failures.jsonl` (Mac) into held-out eval cases + corrected-behavior rows for the target; failure categories steer coverage and chunk priority. Distill `~/mlx-lm-lora/successes.jsonl` into positive training rows + operator-corpus material — success rows are TRAIN-side only, never eval (eval stays hard); only VERIFIED successes are entries, proof included. Both agents feed both ledgers; Hermes is a first-class source (his session/decision history, fixes, distillations), not just the datasets. **Sources overall — five families, one pipeline:** the fleet's corpora; fleet experience (both ledgers); **agent skill libraries** — Juno's skills AND Hermes' skills distilled into procedural/scenario rows + eval cases (snapshot per curation, generalize paths, prefer skills tied to verified outcomes; Hermes is self-improving, so his library is a living corpus whose revisions are improvement trajectories — and he distills his own skills locally on prep nights); public HF datasets staged under `/Volumes/Sabrent/datasets/hf/` (OpenHermes-2.5, glaive-function-calling-v2, SlimOrca, s1K, Pasta009… — license + repo/revision in the manifest, privacy screen still applies, sample-inspect first, overnight downloads only, NEVER re-upload someone else's set or a derivative as original); teacher-generated material from the frozen tier. Tracks: **the MAIN track is actual improvement on everything** — the fleet's real work across the board, fed by the corpora + the failure ledger. Cannabis/CannaAI is one specific track inside it (strains + science Q&A → MiniCPM-V 1B text route / Ornith 9B; own-grow diagnostics set still to build) — a rotation slot, never the program's headline. **RSI operator track (PLANNED, added by Duckets 2026-10-22):** train Ornith 9B on the program itself — run plans, the failure AND success ledgers, Bolt's studio.db run history (16 runs, errors included), and Juno + Hermes training-decision history incl. Duckets' corrections and the decisions that verifiably worked — into a drafting / log-watching operator on its own `<model>-op-v<n>` chain, judged at its own eval gate. It proposes, never fires: the no-start_training-without-Duckets'-order rule binds it exactly as it binds Hermes. First step is a prep-night corpus inventory + curation (eval held out first; backup under `datasets/rsi/ornith-1.5-9b-operator/`).
3. **Back up** — `tools/backup_dataset.py OUTDIR <target>` → `/Volumes/Sabrent/datasets/rsi/<target>/<date>-v<n>/`, size-verified, append-only. No verified backup = no run. Train from the backed-up copy. (mlx-lm-lora wants a data folder with `train.jsonl` + `valid.jsonl`: when staging the run folder from the backup, ALSO copy eval.jsonl → valid.jsonl there; the gate still scores against the untouched eval.jsonl in the backup.)
4. **Validate** — MCP `check_training_config` must pass before `start_training`, always.
5. **Train** — FROM the parent version's **bf16 merged master** (latest verified `<model>-rsi-v<n>` per `hidden_files/lineage-<model>.md`; base for v1 — the bf16 master is always the lineage's source of truth; quantized serving copies are derived, never parents; LoRA-on-quantized is QLoRA-style, not QAT), sized to finish well inside the window (big datasets chunk across nights, one chunk per run); hyperparameter carry-over per the run plan (LR re-warm to a fraction of prior peak + re-decay; α=2r; rank non-increasing along the chain; seeds/data order in the manifest); poll `training_status`/`training_log`; 09:45 = `stop_training`, no exceptions (training done by 10 AM is Duckets' hard rule). **Anti-degradation pair (Duckets, 2026-10-22):** (i) every curated train set carries a ~10–15% general replay slice (see PROGRAM.md curation §7) so general skills rehearse on every run; (ii) the **fresh challenger** — when a chain hits a trigger (2 straight gate losses, drift ≥ half the drift line, or every 4th kept version), a planned sequence trains FRESH from base on the chain's accumulated data and faces the chain head at the full gate (target eval + frozen suite + GPQA); winner takes the chain (a winning challenger is logged as a fresh-restart version), loser is discarded with numbers. Either way the face-off is recorded in the ledger — it's the program's running evidence on whether compounding still helps that model.
6. **Eval gate + anti-lobotomy guard (Duckets, 2026-10-22; statistics per the 2026-10-22 research pass)** — TWO mandatory post-run tests, no exceptions, all scored on the **SERVING artifact** through the production configuration (adapter / bf16-merged / serving scored separately; serving decides): (a) candidate vs **parent** on the held-out SELECTION eval — kept only on a win ≥ the pre-set margin (≥2× paired SE; ties keep the parent; a sub-margin win earns one seed-repeat; ≤3 pre-declared checkpoints, no fishing; the CONFIRMATION set is touched only at milestones and challenger face-offs, which are judged on it); and (b) the **frozen regression suite** — now including the safety/refusal domain and per-chunk probes, with PER-DOMAIN drift floors vs base (not one aggregate line) plus drift signals (general-text PPL, output length, distinct-n, refusal rate). Plus the **benchmark evidence layer** (Duckets, 2026-10-22): every kept version gets a benchmark record from **battery v2** — one benchmark per capability area (GPQA Diamond = reasoning/science, VERIFIED harness at `~/workspace/bench/official/gpqa_diamond_parallel.py` run from the VM against the LM Studio API key file, never print that key; then IFEval, MATH-500, HumanEval+, BFCL, MMLU, GSM8K, TruthfulQA, ARC-Challenge joining one at a time as each runner verifies; MMMU when the vision track activates; tier rule — a benchmark counts only where the base beats its floor) recorded in its lineage ledger; benchmarking runs mostly on NON-training nights via cron `rsi-benchmark-nights` (Mon/Wed/Fri/Sun 01:00, stands down when a training/smoke job owns the night, restores the LM Studio loaded set exactly, battery may split across nights per model). Benchmarks are evidence under the hard gates, not a third gate (yet); a crater vs parent triggers the keep/remove review. Benchmark items are eval-only, never training data. Datasets and versions alike earn their keep by measured effect — prep nights retire what repeatedly fails to move eval/benchmark numbers (archive + note in rotation state, never silent reuse). (fixed general-capability set — instruction following, reasoning, coding, tool use, conversation + the failure-ledger eval cases; built once, backed up under `datasets/rsi/frozen-suite/` on Sabrent, NEVER trained on, NEVER edited to make a run pass) scored vs parent AND vs base v0. Winning (a) while regressing on (b) = discarded, same as a gate loss — versions train on top of versions here, and small general losses compound into a lobotomized model. Record parent / base / candidate frozen-suite scores in the lineage ledger after EVERY run; cumulative drift vs base is a named number in the morning report. Any clear regression on a frozen category vs parent fails the candidate; crossing the lineage's pre-set cumulative drift line stops the chain — the next run restarts from base or the last known-good version. Never build the next run on a regression.
7. **Deploy + verified swap** — merge the kept adapter, install into the LM Studio library as `<model>-rsi-v<n+1>`, verify IN LM Studio (load, real prompts incl. eval prompts, image test for vision models, quality vs parent). Only after it verifies: previous RSI version moves to `/Volumes/Sabrent/lmstudio-archive/` (never hard-delete; the original base always stays). Failed verification → new model pulled, old one untouched, failure reported plainly. Update the lineage ledger either way.

## Driving the MCP
Server: `/Users/duckets/mlx-lm-lora/.venv/bin/mlx-lm-lora-mcp` (Mac). One-shot driver: `tools/rsi_mcp.py` (runs on the Mac; call it through `~/bin/mac-ssh`):
```
~/bin/mac-ssh "python3 ~/mlx-lm-lora/tools/rsi_mcp.py list-tools"
~/bin/mac-ssh "python3 ~/mlx-lm-lora/tools/rsi_mcp.py check_training_config '{\"config\": {...}}'"
```
Tools: list_training_modes, check_training_config, start_training, training_status, training_log, list_training_runs, stop_training. Handshake fallback/test: `~/mlx-lm-lora/mcp-test.py`. If the driver hangs, check whether the server is waiting on stdin EOF — kill the driver, not the server config; never restart LM Studio to fix MCP.

## Memory discipline + gotchas
- Training nights are NOT full training-mode lockdowns (that's for Duckets' big manual runs) — but the Mac discipline still applies: check what's loaded before anything, leave nothing running afterward, downloads (Gemma set) happen overnight only.
- Hermes brain jobs (~3 AM) and Hy-Memory shadow (3:38 AM) share these nights by design — that's why preflight waits instead of forcing.
- A "successful" start_training return is not proof of training: confirm via training_status + log lines (same lesson as the Unsloth zombie runs).
- Adapters that don't face the eval gate don't count. Unevaluated adapter piles are clutter, not progress.
- Smoke night rule: the first run of any new target/toolchain version is tiny and proves the pipeline only — no eval claims, no deployment.
- Benchmark comparability: same harness, same settings, same battery version — a GPQA score from a different harness/config is a different metric. Reference on record: DuckBot Ornith 35B = 111/198 (56.1%), 2026-10-08. Battery expansion (MATH-500, HumanEval+, IFEval, MMLU) only one at a time, runner verified on a known model first.
- Driver invocation: run `rsi_mcp.py` in a FOREGROUND mac-ssh call with a generous yield, one driver at a time. Two concurrent drivers (or a backgrounded one racing a retry) can make the server look hung/EOF — if it ever reports a transport error, wait, check for stray driver processes on the Mac, and retry once cleanly before touching any config.
