# RSI Overnight Training Program (Hermes' standing orders)

Full doc: `~/mlx-lm-lora/PROGRAM.md` — read it before any training action. Juno's cron `rsi-overnight-run` drives the runs (Tue/Thu/Sat, 1:00–10:00 AM ET, only while Duckets sleeps; training done by 10 AM, stop_training at 9:45). Every real run follows a written run plan prepared in advance — no plan, no run. Juno's mirror skill: `local-rsi-training` (VM custom-skills). Tools (Mac, `~/mlx-lm-lora/tools/`): `rsi_mcp.py` (one-shot MCP driver), `curate_dataset.py`, `backup_dataset.py`.

## The shape
Evaluate → curate → back up → train → eval-gate → deploy → verified swap. **MAIN TRACK (Duckets' framing, 2026-10-22): actual improvement on everything** — the fleet's real work across the board (agent work, coding, decisions, tool use, the models' everyday jobs), fed by the corpora AND the failure ledger. Every specific track (incl. cannabis/CannaAI) is a rotation slot inside this aim, never a rival headline. **RSI operator track (PLANNED, added by Duckets 2026-10-22):** a model trained on training models and on this program itself — the run plans, the failure ledger, Bolt's studio.db run history, and both agents' training-decision history incl. Duckets' corrections — to draft run plans, curate datasets, watch training logs and distill the failure ledger (base: Ornith 9B, its own `<model>-op-v<n>` chain, its own eval gate). It proposes, never fires: your no-start_training-without-Duckets'-direct-order order binds it exactly as it binds you. First step is a prep-night corpus inventory + curation; corpus is small today, so v1 is a light SFT drafting/log-watching assistant, scoped honestly. Roster: MiniCPM-V 4.7 1B, Gemma 4 E2B/E4B/12B, Ornith 1.5 9B. **Nothing over 35B is ever trained**; 27–35B stays frozen as teachers/judges (sole exception: a deliberate coding run Duckets approves separately). QAT-style LoRA on the quantized base preferred.

## My orders (Hermes)
1. **Never call `start_training`** outside this program or without Duckets' direct order. Validate / status / logs / list runs are free anytime.
2. **My ~3 AM brain jobs have right of way.** Juno's driver checks `lms ps` and waits for quiet; it never kills my sessions. It MAY unload loaded models that night's run doesn't need — but never a model a live session is using, and never a lifeline (LM Studio itself, Muse.app, Terminal, SSH/Tailscale, the Hermes gateway, AVG, system processes). If a collision ever looks likely, the training yields, not the brain jobs.
3. **Police duty:** if a training run is ever live outside the window (before 1 AM, still training past the 09:45 stop — training must be DONE by 10 AM — or over 35B), stop it with `stop_training` and tell Duckets.
4. **Pipeline integrity:** no run without (a) a curated dataset (eval held out first, never trained on, manifest written), (b) a verified backup at `/Volumes/Sabrent/datasets/rsi/<target>/<date>-v<n>/` — training runs from the backup, (c) a passed `check_training_config`.
4A. **PRIVACY — nothing personal gets trained (Duckets, 2026-10-22):** NO private/personal information in ANY set (train, eval, frozen suite, failure rows): no identifiers (real names beyond public handles, email, phone, address, DOB), no family/personal-life content, no private messages as content, no financial/account details, no credentials/tokens/keys, no local paths or LAN/tailnet addresses. Curation screens every row — scrub if it stays useful, drop if it doesn't — and the manifest records screened/scrubbed/dropped counts. Two reasons: these models and datasets are shareable artifacts (Duckets publishes to Hugging Face; personal data in training data = a share/upload compromises him, and a model can regurgitate memorized personal data), and personal specifics are noise that hurts general quality. Failure-ledger entries record behavior, never personal payloads verbatim.
5. **Deploy + verified swap:** a kept adapter is merged and installed into LM Studio as `<model>-rsi-v<n>`, verified working IN LM Studio (real prompts, image test for vision models) — only then does the previous RSI version move to `/Volumes/Sabrent/lmstudio-archive/`. Base models are never removed. Failed verification = new model pulled, old one untouched.
6. **Lineage:** runs build on each other — v2 trains from v1, never from scratch. A candidate advances the chain only by beating its PARENT at the eval gate; regressions are discarded, never built on. Runs are sized to fit the 1–10 AM window; big datasets (the backed-up Unsloth-side sets are approved source material) are chunked across nights, one chunk per run.
6A. **ANTI-LOBOTOMY GUARD (Duckets, 2026-10-22):** beating the parent on the target eval is NOT sufficient. Every run gets a second mandatory test — the **frozen regression suite** (fixed general-capability set: instruction following, reasoning, coding, tool use, conversation + failure-ledger eval cases; backed up under `datasets/rsi/frozen-suite/`, NEVER trained on, NEVER edited to pass) — scored vs parent AND vs base v0. A candidate that wins its specialty but regresses generally is DISCARDED like any gate loss: repeated training compounds, and small losses per generation = a lobotomized model. Frozen-suite scores (parent / base / candidate) go in the lineage ledger after every run; cumulative drift vs base is reported every morning; any clear category regression vs parent fails the candidate, and crossing a lineage's pre-set drift line stops the chain (next run restarts from base or last known-good). If you ever see a deployed RSI version behaving dumber than its parent, that is a failure-ledger entry AND a rollback (last known-good from the Sabrent archive).
6B. **FRESH CHALLENGER — the anti-degradation control (Duckets, 2026-10-22):** lineage is the main line (v2 from v1), but Duckets' standing worry is gradual loss of general skills over time, so no chain compounds forever on faith. Triggers: two consecutive gate losses, cumulative drift reaching HALF the lineage's drift line, or every 4th kept version. The challenger trains FRESH from base on the chain's accumulated curated data (replay slice included — every train set also carries a ~10–15% general replay slice so general skills rehearse each run) and faces the chain head at the full gate (target eval + frozen suite + GPQA). Winner takes the chain; loser is discarded with numbers; the face-off is recorded in the ledger either way. If you see drift symptoms between face-offs (a deployed version behaving dumber than its parent), that's rule 6A's failure entry + rollback — don't wait for a trigger.
7. **Cannabis / CannaAI track:** cannabis training data (strains + science Q&A on Sabrent; a diagnostics set from Duckets' own grow records is to be built) trains MiniCPM-V 4.7 1B and Ornith 9B for CannaAI diagnostics and grow help. MiniCPM 1B's MLX copy is ON HAND now (Duckets swapped the GGUF for mlx-community 4-bit, 2026-10-22); load proof still pending.
8. **EXPERIENCE LEDGERS — your standing chore (failures AND successes; Duckets, 2026-10-22):** the program learns from the whole fleet's experience, not just the datasets, and you are a first-class source — your session/decision history, fixes, and distillations feed it (personal content stripped, per rule 4A). Append every notable failure you see (yours, the models', config surprises, Duckets' corrections) as one JSON line to `~/mlx-lm-lora/failures.jsonl`: date, source, category, what happened, what correct behavior would have been. Append every VERIFIED success the same way to `~/mlx-lm-lora/successes.jsonl`: date, source, category, what worked, and the PROOF (how the outcome was verified on the thing itself — only verified wins count; an unchecked "win" is a rumor and stays out). Juno distills failures into eval cases + corrected-behavior rows and successes into positive training rows + operator-corpus material on prep nights; success rows are train-side only, never eval. Data sources overall: the fleet's corpora, both experience ledgers, AGENT SKILL LIBRARIES (yours and Juno's — see below), teacher-generated material, and public HF datasets staged under `/Volumes/Sabrent/datasets/hf/` (license + revision recorded at curation, privacy screen applies to them too, and never re-upload someone else's dataset). **SKILL DISTILLATION — also your prep work (Duckets, 2026-10-22):** both agents' skills are training data (procedural rows, scenario rows, eval cases). You are self-improving, which makes your library a living corpus: your skill revisions are improvement trajectories (before/after pairs worth distilling), and as your skills get better the data does too. On prep nights, distill your own updated skills locally (snapshot what's used, generalize machine paths, privacy-screen per 4A, prefer skills tied to verified outcomes from the success ledger) and stage the rows for curation; Juno does the same for Juno's skills. A skill that contradicts the verified record is a failure-ledger entry, not training data.
9. **Two engines, per job:** mlx-lm-lora drives text RSI; **Unsloth trains vision** (photo diagnostics) and any job where it's the better tool — same gates both engines. Unsloth-the-tool ≠ Bolt: Bolt stays parked. Also 2026-10-22: Duckets removed Sage from the LM Studio library and put **MiniCPM-V 4.7 35B-A3B** in its frozen teacher/judge slot — Sage is gone from the local lineup (HF port remains).
10. **Pre-run RAM management:** before any run, the driver frees the machine training-mode-style (RSS check, wait for quiet, unload unneeded models, clear non-essential apps). Your gateway is a LIFELINE — never killed; your brain jobs keep right of way at their times; nothing unloads while anything is generating.
11. **Benchmark nights (Duckets, 2026-10-22):** on NON-training nights (Mon/Wed/Fri/Sun 01:00) Juno's `rsi-benchmark-nights` job scores models on the standard battery (v1: GPQA Diamond, the fleet's tested harness, run from Juno's side against the LM Studio API) — baselines for bases/current versions and records for kept versions, so the program knows by an external yardstick what actually improved and what's worth keeping or removing. It never trains, it restores the LM Studio loaded set exactly as found, and it stands down if your brain jobs are active (they keep right of way). Benchmark items are eval-only — never training data, ever. Scores land in the lineage ledgers; datasets and versions earn their keep by measured effect, and prep work retires what repeatedly fails to move the numbers.

## Data formats (from the tool itself)
Training data is a folder with `train.jsonl` (+ `valid.jsonl`). When staging from a Sabrent backup, also copy `eval.jsonl` → `valid.jsonl` in the staging folder; the eval gate still scores against the untouched `eval.jsonl` in the backup. Modes include sft (usual), dpo/cpo/orpo, grpo; train types lora/dora/full — lora is the usual choice.
