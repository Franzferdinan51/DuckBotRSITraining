# RSI system audit — 2026-10-22

Full-system review performed the night the program was created, at the owner's order: two independent reviewers (one on the driver tools' code, one on the documents/crons/state) plus live verification of the actual Mac install. Findings are reconciled across all three passes — where a reviewer saw only one copy of a file, the live pass checked the other.

**Status key:** FIXED = repaired the same night · OPEN = documented, awaiting fix/decision · WATCH = verified behavior, re-check later.

**Net assessment:** the documents agree on philosophy everywhere. The failures are mechanical: rules written faster than the machinery to enforce them, one stale instruction that would have misfired the Saturday run, and backup coverage that stops exactly where the program's most irreplaceable assets begin.

---

## Critical

### 1. The mandatory privacy screen had zero working implementation — FIXED (process), code fix OPEN
The program's privacy rule (nothing personal gets trained) is enforced, per the docs, by `curate_dataset.py`. Live verification of both copies:
- The driver-side copy had **no privacy code at all** (no patterns, no counters; the manifest cannot produce the screened/scrubbed/dropped counts the docs claim).
- The Mac copy had a `privacy_screen()` function (regexes for email, phone, wallets, API keys, user paths, mesh hostnames, chat IDs — added by the co-agent that same evening) that is **defined but never called**: `main()` never invokes it, and the stats/manifest carry no privacy counters. Dead code that reads as protection.

Until the code fix lands, the overnight cron's instructions were amended the same night: the driver performs the screen during curation (pattern pass + spot review) and records counts by hand, and must never claim the tool did it. **Code fix (priority 1):** wire `privacy_screen()` into `main()` before dedupe, add `screened/scrubbed/dropped` to stats + manifest, and add a names/addresses pass — regexes alone cannot catch a person's name or street address in prose.

### 2. The eval layer is specified as prose and built as nothing — OPEN
The eval gate, the frozen regression suite, and drift tracking all depend on an "evaluate" step that has no tool: no scorer, no eval runner, no prompt-scoring harness, and no named tool for the merge/fuse step the swap rule requires. The MCP's 7 tools are training-only. The first real run plan (2026-10-27 draft) originally described judging by "eval loss plus a fixed set of real decision prompts scored against the base's answers" — scored by whom/what was never stated. The frozen teacher/judge tier exists in the roster; nothing connects it to the gate. `docs/FROZEN-SUITE-SPEC.md` now specifies the suite + scoring procedure; a scorer tool is the program's top build item after the privacy wiring.

### 3. The recurring cron still thought Saturday was the smoke night — FIXED
The recurring driver's saved instructions said "FIRST-EVER run of this program = SMOKE NIGHT," while the smoke had been moved to a Friday one-off and the rotation state called Saturday the first post-smoke night. Left alone, Saturday's driver could have re-run a pointless smoke or misread the night. The cron body now treats the smoke as recorded history (and only falls back to a smoke if no smoke result exists in the record). The same staleness in the lineage ledger's notes was corrected the same night.

### 4. `curate_dataset.py` near-dupe key can silently gut a dataset — OPEN
`near_key()` = the first 200 normalized characters of a row. Fleet corpora are chat rows that typically share a long identical system/instruction prefix; if that prefix is ≥200 chars, **every row after the first with the same prefix is dropped as a "near dupe."** The manifest reports it as deduplication working. Present in both copies. **Fix direction:** key on the last message / strip shared prefixes before keying / hash a mid-text window — and add a sanity alarm when near-dupes exceed a sane fraction of input.

## High

### 5. `rsi_mcp.py` has no timeout — a hung server hangs the driver forever — OPEN
`rpc()` blocks on `readline()` with no deadline; `Popen` sets no timeout. The known failure mode (server waiting on stdin EOF) wedges the one-shot driver indefinitely; in the overnight cron that burns the night until the job-level timeout. No lockfile/single-instance guard either, despite the skill's own "one driver at a time" rule. **Fix:** read deadline + kill escalation, and a pidfile lock.

### 6. `rsi_mcp.py` swallows MCP tool-level errors as success — OPEN
Only JSON-RPC-level `"error"` is checked. MCP `tools/call` failures conventionally return a normal result with `isError: true` — that path exits 0. The cron treats this driver as the authority for `check_training_config` ("must pass before any start_training"), so a failed config check can surface as clean JSON unless the calling agent interprets the content. Mitigated today only by driver diligence (the cron also requires confirming training via status/log lines).

### 7. `rsi_mcp.py` breaks its own exit-code contract on the likeliest failures — OPEN
`json.loads(argv)` and `Popen([SERVER])` both run **before** the `try:` — malformed args or a missing server binary produce raw tracebacks (exit 1) instead of the documented `{"transport_error": …}` + exit 2.

### 8. The first real run plan violated the anti-lobotomy guard it predated — FIXED
The 2026-10-27 draft plan's eval section specified only the target eval — no frozen-suite test, no baselines, no drift line. Executed as written, the first real run would have broken the guard adopted the same evening. The plan now carries the guard section explicitly, including "building the suite is prep work that must land before this run executes."

### 9. The lineage ledger couldn't hold what the guard requires — PARTLY FIXED
The ledger table had no frozen-suite columns and no cumulative-drift column, and **no drift-line value existed anywhere**, though the guard requires each lineage's line be recorded *before* its first real run. The repo's ledger template now carries the columns + a drift-line field; the live Ornith ledger notes the line as NOT SET YET — setting it is an owner decision still owed before the first real run.

### 10. The frozen regression suite does not exist — OPEN
No suite file, no baselines. The cron already treats building it as prep work that outranks a real run for lineages past v1; the spec now exists (`docs/FROZEN-SUITE-SPEC.md`). Until it exists, no chain may advance to v2 — by the program's own rule.

## Medium

### 11. Two sources of truth for the tools, already diverged — PARTLY FIXED
The tools live in the driver's skill folder AND on the Mac; nothing versions or syncs them. Within five hours of creation they diverged: the co-agent fixed a real bug on the Mac (a leaked `PYTHONPATH` from its runtime broke the MCP server's `import mcp`; the driver now strips it for the child) and added the (unwired) privacy function — while the driver-side copies stayed stale. The driver copies were refreshed from the Mac the night of this audit, and this repo ships the Mac-current code. **Still open:** a standing sync/checksum procedure (RECREATE.md §5 names one; nothing enforces it).

### 12. `backup_dataset.py` weaknesses — OPEN
- A failed verification leaves the partial `<date>-v<n>` folder in place, permanently consuming that version number and sitting in the tree indistinguishable from a good backup. No cleanup, no `.incomplete` marker.
- "Verification" is byte-size only — no hash. The program treats a passed backup as the integrity gate for training.
- The `target` argument is unvalidated: `../../…` writes outside the RSI tree, in the tool whose job includes the strict RSI/Unsloth tree-separation rule.
- It copies exactly 3 hardcoded filenames (train/eval/manifest) — anything else is silently skipped; the frozen suite's shape can't be backed up by it at all.
- Default root is one specific external volume; on a machine without it, the failure is an uncaught traceback or a look-alike tree, never a clean message.
- No free-space precheck.

### 13. `curate_dataset.py` robustness — OPEN
- Crashes on valid-JSON-but-non-dict lines (`row.get` on a list/string) instead of counting them malformed — raw scraped corpora are exactly where stray scalar lines occur; the run dies mid-file with no outputs.
- Can emit an **empty train set and report success** (1 kept row → eval takes it, train = 0; the empty file then passes the backup tool's size check and the pipeline "trains" on nothing). No minimum-train-size guard in either tool.
- Manifest is thinner than the docs require: no date, no dataset version, single source path, no per-filter "why."
- No chunking support (`--chunk/--offset/--limit`) despite the program's chunk-across-nights rule — chunking is manual and unrecorded.
- Whole-file reads (several× file size peak memory): fine on the 128 GB reference machine, a real risk on a smaller one.

### 14. Driver protocol fragility — OPEN
`rsi_mcp.py` treats any non-JSON stdout line from the server (banner, warning) as a transport error; `protocolVersion` is hardcoded; the child is terminated without wait/kill escalation (a SIGTERM-ignoring server leaks a process per call); server stderr is inherited, interleaving diagnostics into the driver's output. Also **finding A20:** the skill's example calls `check_training_config` with `{"config": …}` while the tool's own docstring shows `{"config_path": …}` — one disagrees with the server's real schema; the smoke night's config validation will reveal which.
