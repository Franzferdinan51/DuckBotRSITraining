# RSI Overnight Small-Model Training Program
### Set up 2026-10-22 at Duckets' order. The loop: evaluate → train → evaluate → iterate.

## The rules (Duckets', not negotiable)
- **Size ceiling: nothing over 35B is ever trained.** Smaller models improved a lot beats rare giant runs.
- **Runs happen only while Duckets is asleep.** Window: **1:00 AM – 10:00 AM ET** (Duckets, 2026-10-22: training must be DONE by 10 AM). Training still running at 9:45 AM is stopped via stop_training, no exceptions; eval/deployment/report wrap inside the window.
- **Cadence: 3 nights a week — Tue / Thu / Sat (1:00 AM starts).** One model, one job per night.
- **Every real run is a PROPER run, prepared in advance** (Duckets' standing emphasis: "we gotta prepare a proper run for actual improvements — all the details matter"). A real run executes a written run plan (below) — never an improvised 1 AM invention. An underprepared night becomes a prep night, and that's a good outcome, not a failure.
- **Runs are sized to FIT the window** (Duckets, 2026-10-22). The run plan budgets steps from measured/estimated throughput so training completes well inside 1–10 AM with room for eval + deployment. If the material is a big dataset, it is **broken into chunks across multiple nights** — one chunk per run, each chunk its own curated, backed-up dataset version — never one oversized run that has to be killed at the deadline.
- **Build on every run — version lineage** (Duckets, 2026-10-22). Runs on a model form a chain: v1 trains from the base, v2 trains from v1, and so on. Each run starts from the **latest verified version** of that model, not from scratch, so improvement compounds. A version earns its place only by beating its **parent** at the eval gate; a regression is discarded and the chain stays at the last good version — we never build on a regression. Models are labeled by version everywhere (see Deployment & swap): `<model>-rsi-v<n>`, with the full lineage recorded in a ledger. Chains are periodically challenged by a fresh-from-base control run (see The fresh challenger) — compounding must keep proving itself against Duckets' standing worry: gradual loss of general skills over time.
- **The backed-up Unsloth datasets are fair game as source material** (Duckets, 2026-10-22) — e.g. the code/decision corpora under `<datasets-root>/unsloth-source/` or the Sabrent merged corpus. They enter the RSI pipeline the normal way: curated into an RSI dataset version and backed up under `datasets/rsi/` before training (the separation rule still holds for the curated output).
- **Public Hugging Face datasets are fair game too** (Duckets, 2026-10-22, confirming the system's data sources) — staged under `<datasets-root>/hf/` (the fleet already holds OpenHermes-2.5, glaive-function-calling-v2, SlimOrca, s1K, Pasta009 and others there from the DuckBot training era). Same pipeline, no exceptions: license checked and recorded in the manifest (repo id + revision too), quality-filtered hard (public sets vary wildly), privacy screen applied anyway (public ≠ clean — scraped sets carry PII), sample-inspected before a full curation, downloads overnight only. **Use is not ownership: never re-upload someone else's dataset — or a derivative passed off as original — to Hugging Face; training on them is fine, republishing is not.**
- **Eval gate:** an adapter is kept only if it beats its **parent version** on that job's eval set (for v1, the parent is the base model) **by the pre-set margin — at least 2× the paired standard error of the difference** (research amendment, 2026-10-22: a bare "beats parent" at small eval sizes is a noise ratchet; ~785 paired items detect a 5-pt real difference, ~2,200 for 3 pts). A tie keeps the parent; a win smaller than the margin earns ONE seed-repeat (different seed/data order) before acceptance, and the repeat decides. Otherwise it's discarded and the night is logged as a loss with a reason. Unevaluated adapters never accumulate.
- **QAT where possible/helpful:** prefer training against the quantized base (LoRA on quantized weights) for models that ship quantized, so gains survive quantization.
- **start_training is a commitment action:** inside this scheduled program, a run may start only when ALL of these hold: (1) a written run plan for tonight's target exists, (2) a curated dataset AND held-out eval set exist for it, privacy-screened with the counts in the manifest, (3) the curated set is backed up under `datasets/rsi/` and verified, and (4) `check_training_config` passes. If any is missing, the night is prep work (plan writing, dataset/eval building, config validation) and a report — never an aimless run.
- **Datasets are curated before every run** (see below) — no raw dumps go straight into training.
- **Datasets are backed up to the external drive before training** — curated datasets are fleet assets, reusable for future bigger models or new models we switch to.
- **LM Studio gets the new model after training, and the old one is removed only after the new one is verified working in LM Studio** (see Deployment & swap). The base model is never the thing removed — the swap replaces the previous RSI version.

## The run plan (written before every real run)
A real run executes a plan saved at `<repo>/templates/run-plan.md<date>-<target>.md` in this goal's workspace, naming: target model + the specific job it is being improved for; the **parent version** it builds on (the latest verified `<model>-rsi-v<n>`, or the base for v1); the exact curated dataset version (Sabrent backup path) — and if the source material is large, **which chunk this run covers (chunk k of m)** and where the remaining chunks sit in the rotation; training mode/type (sft/lora usual); key hyperparameters; a step budget with the throughput math showing it finishes well inside the 1–10 AM window; the held-out eval set + the metric that decides keep/discard (the candidate must beat its **parent**, not just the original base); and the deployment name (`<model>-rsi-v<n+1>`). Plans are written during prep nights (or daytime prep), reviewed against this doc, and only then executed. If any element of the plan is missing at window-open, the night is a prep night that completes the plan.

## Dataset curation (before any run, every run)
Raw material is never trained on as-is. **Sources, all five families, all through this same pipeline:** (1) the fleet's own corpora (code/decision sets, the merged corpus, domain corpora); (2) **fleet experience** — the failure ledger AND the success ledger, distilled from both agents' work (see Experience-driven improvement); (3) **agent skill libraries** — Juno's skills AND Hermes' skills, distilled (see Skill libraries, below); (4) **public Hugging Face datasets** staged under `datasets/hf/` (license + revision recorded in the manifest; never re-uploaded); (5) teacher-generated material from the frozen 27–35B tier. Before a run night's training starts:
1. **Clean:** drop malformed rows, empty/degenerate outputs, and near-duplicates; fix formatting to the target's chat format.
2. **Filter for quality:** keep examples that actually demonstrate the job (correct, complete, in Duckets' style where that's the point); cut the bottom tail rather than padding the count.
3. **Balance:** don't let one source or one task type swamp the set.
4. **Split:** hold out the eval set FIRST and never train on it — the eval gate is meaningless otherwise.
5. **Version it:** every curated set gets a version + a manifest (sources, row counts before/after, what was filtered and why, date). If curation can't produce a set worth training on, the night becomes a prep night and the report says so.
6. **Lifecycle — datasets earn their keep (Duckets, 2026-10-22):** as versions stack up, the record shows what actually moved the numbers. The lineage ledger ties every version to the dataset version + chunk that produced it and its eval/benchmark results; prep nights review that record. A dataset (or chunk family) whose runs repeatedly fail to improve eval/benchmarks is retired — moved to the archive, noted in the rotation state, never silently reused. The same evidence governs the model roster: a base that never produces a kept version leaves the rotation. Nothing is deleted in anger and nothing is kept on faith — measured effect decides.
7. **Replay slice (anti-forgetting, Duckets 2026-10-22; composition corrected by the 2026-10-22 research pass):** every curated train set carries a replay slice in TWO parts — **~5–8% general** (instruction following, reasoning, conversation) **plus ~10–20% stratified replay of ALL PRIOR TARGET CHUNKS** of this chain. The evidence is explicit that replay protects what it replays: general-only replay guards general capability (which the frozen suite already measures) but does almost nothing for chunk-1 skills being overwritten by chunk k — the chain's actual workload. Proportions are recorded in the manifest. The fresh challenger (below) remains the periodic proof.
8. **Decontamination (research amendment, 2026-10-22):** every new source is checked against ALL gate material — target eval sets, the frozen suite, and every benchmark in the battery — by n-gram overlap PLUS embedding top-k similarity with spot checks, because rephrased contamination evades n-grams entirely (a 13B fine-tuned on rephrased MMLU/HumanEval items scored at GPT-4 level while passing n-gram screens; teacher-generated data is a known vector). The measured contamination rate is logged in the manifest; flagged rows are dropped, never scrubbed-and-kept.
9. **Provenance + synthetic budget (research amendment, 2026-10-22):** every row carries provenance (source family, generating model/teacher if any, verifier if any) in the manifest. Synthetic data (teacher/agent/self-generated) **accumulates alongside real data, never replaces it**: the real-data share never shrinks in absolute rows from one generation to the next, and the synthetic share per curated set is capped (default ≤50%, stated in the run plan). "Verified" rows require a verifier independent of the model/agent that generated them — self-graded successes are unverified data. Prep nights watch the tails (distinct-n, output-length distribution, rare-slice accuracy), where collapse shows first.
10. **Filter honesty (research amendment, 2026-10-22):** quality filters are bands, not hard cutoffs, where the tool supports it; the manifest logs composition before/after filtering, and prep nights sample-audit REJECTED rows — filters (perplexity especially) bias the topic mix and preferentially retain AI-generated text.
11. **Feasibility by replay (AgentEvolver import, 2026-10-22):** a synthetic or teacher-generated row whose outcome is checkable ships only if its reference solution ACTUALLY EXECUTES — code runs, the tool call validates, the calculation recomputes. Execution is the strongest form of the independent verifier §9 requires; judge approval alone doesn't make a row "verified" when an execution check exists. Their evidence for the payoff: synthetic-only data trained ≈ human-curated data, and hybrid synthetic+real beat real-only — the empirical backing for our synthetic cap + never-shrink-real rules.
12. **Difficulty-parameterized synthesis + task schemas (AgentEvolver / CuES import, 2026-10-22):** for a data-poor track (own-grow diagnostics is the standing example), don't free-generate rows. Build the domain's **environment profile** first — its entities, attributes and operations — synthesize tasks on a **difficulty ladder** by scaling those three counts, and abstract patterns that work into reusable **task schemas** instead of one-off rows. Volume discipline from their quantity curve: ~100 good tasks captured most of the gain and 200→500 showed clearly diminishing returns — small, diverse, verified sets beat bulk, which is also what our chunk economics and the ~4-exposure retirement rule assume.
13. **Step attribution as row surgery + train as you'll serve (AgentEvolver import, 2026-10-22):** multi-step traces (agent sessions, Hermes trajectories) get step-level GOOD/BAD labels from a strong frozen-tier judge before distillation: rows are dropped or truncated at the first BAD step instead of training on whole flawed trajectories, and the GOOD segments of FAILED trajectories are mined as positive rows — a failed trajectory is not a wasted trajectory. Rows generated WITH retrieved guidance (ledger units, skill text) enter training with the guidance REMOVED, so the model internalizes the behavior instead of learning to depend on hints it won't have when serving. And the mix-balance evidence behind our caps: guidance at ~half the mix was optimal in their sweeps and more guidance won early but lost late — no single guiding source (replay, teacher rows, experience rows) should exceed ~half a chunk.
14. **Datasets evolve — the data is the ceiling (Duckets, 2026-10-23):** a model can only be as good as its training data, so datasets are expected to CHANGE across generations while the objective stays fixed (same eval, same frozen suite, same gates). Each generation's curation modifies the set against the current model's measured weaknesses: failures mined into corrected rows, mastered rows retired via the exposure counter, difficulty ratcheted up the ladder, dead sources culled under §6. A static dataset trains a static model — dataset versions advance alongside model versions, and the lineage ledger records both.

## Privacy — nothing personal gets trained (Duckets, 2026-10-22)
His rule, with his two reasons: (1) **these models and datasets are shareable artifacts** — Duckets publishes to Hugging Face, and an RSI version or dataset can be shared/uploaded the same way; if personal information is in the training data, sharing it = instantly compromised, and a trained model can regurgitate memorized personal data. (2) **Quality** — personal specifics are noise: they don't generalize, and a model busy memorizing Duckets' details is worse at the actual work, not better.
- **Barred from every set — train, eval, frozen suite, failure rows, no exceptions:** personal identifiers (real names beyond his public handles, email, phone, home address, DOB), family and personal-life content, private messages/conversations as content (his chats, Telegram/Hermes sessions), financial/trading account details, identifying grow-site specifics, and all credentials, tokens, keys, local machine paths, and LAN/tailnet addresses.
- **Enforcement lives in curation:** every row passes a privacy screen before it enters a curated set — scrub the row if it stays useful scrubbed, drop it if it doesn't. The manifest records screened / scrubbed / dropped counts, and a set with an unrecorded screen doesn't train. This codifies the 2026-10-16 precedent: the three-pass privacy verification run before the dataset uploads (personal rows dropped, token-shaped strings scrubbed, remaining hits hand-verified).
- **Sources are screened at curation, every time** — no dataset inherits a "probably clean" from its source corpus, however often that corpus has been used before.
- **Operator-track consequence:** its corpus is session history — mine it for DECISIONS and corrected behavior, strip the personal content; a decision row that can't be separated from its personal payload doesn't ship.
- **Failure-ledger hygiene:** entries record behavior (what happened, what correct looks like), never personal payloads quoted verbatim.

## Dataset backup (external drive, before training)
- The curated train set + held-out eval set + manifest are copied to **`<datasets-root>/rsi/<target>/<date>-v<n>/`** BEFORE training starts, and training runs from that backed-up copy — if the backup fails, the run does not start.
- Why: datasets outlive models. A set curated for a 9B today is the starting material for a bigger model later or a new model we switch to. Losing them means re-curating from raw every time.
- Backups are append-only: new version, new folder; never overwrite a previous version.
- **Separation rule (Duckets, 2026-10-22): RSI datasets and Unsloth datasets are kept strictly separate on the external drive.** RSI curated sets live ONLY under `<datasets-root>/rsi/`. The Unsloth-side source sets (the merged/experiment corpus the Bolt runs trained on) are backed up under **`<datasets-root>/unsloth-source/`** (first copy made 2026-10-22, size-verified per file). Neither side's sets get mixed into the other's tree, and Unsloth Studio's own upload copies stay in `~/.unsloth/studio/assets/` where the app expects them.

## Deployment & swap (after a run whose adapter passes the eval gate)
**Duckets' swap rule, in his words (2026-10-22): delete the old model and add the new one ONLY after testing it — if the new model fails testing after a training run, the old working model is NOT deleted; if the new model works, it DOES go into LM Studio.** The old working model is never removed on a failed test — full stop. ("Delete" here means removed from the LM Studio library; the removed version is archived on Sabrent, not hard-deleted, so a swap stays reversible.)
1. Merge/fuse the kept adapter into the model and install it into the **LM Studio library** under its lineage name: **`<model>-rsi-v<n>`** (v1, v2, v3… — the number IS the version label; dates and parentage live in the ledger, not the name).
2. **Verify in LM Studio itself** (the stack rule: it counts only when it works where Duckets runs it): load it, run real prompts — including the target's eval prompts — and for vision models an image test. Check output quality against the parent version, not just that it loads.
3. **Only after the new model verifies working** is the previous RSI version of that model removed from the library (moved to the Sabrent archive, not hard-deleted, so a bad swap is reversible). The original base model always stays.
4. **Record the lineage** in `<repo>/templates/lineage-<model>.md`: version, date, parent version, dataset version + chunk, steps, eval result vs parent, LM Studio name, status (current / archived / discarded). The next run on that model starts from the ledger's latest verified version.
5. If verification fails, the new model is pulled, the old one stays untouched, and the morning report says exactly what failed. A failed swap is reported as a loss, never quietly retried in a loop.

## Anti-lobotomy guard (Duckets, 2026-10-22)
His concern, in his words: since we're building on top of models we'll be training multiple times, we always have to run tests after a run to make sure the model didn't get lobotomized. Correct — the existing gate alone (beat parent on the TARGET eval) is not enough: a candidate can win its specialty while quietly losing general ability, and ten generations of small losses is a lobotomy by inches. So:
- **Frozen regression suite:** a fixed, held-out capability test set — general instruction following, reasoning, coding, tool use, conversation, plus the failure-ledger eval cases — built once, versioned, and backed up on Sabrent under `datasets/rsi/frozen-suite/`. It is NEVER trained on and NEVER edited to make a run pass; changing it takes Duckets' order and re-baselines every recorded score.
- **Two tests after every run, both mandatory, no exceptions:** (1) the target eval vs parent (the existing gate), and (2) the frozen suite, scored vs parent AND vs base v0. A candidate that wins (1) but regresses on (2) is discarded exactly like a gate loss — never deployed, never built on, chain stays at the last verified version.
- **Drift ledger:** parent / base / candidate frozen-suite scores are recorded in the model's lineage ledger after every run, passed or failed, and **cumulative drift vs base is a named number in every morning report** — slow drift shows up on paper before it shows up in conversation.
- **Circuit breaker:** any clear regression on any frozen-suite category vs parent = fail, no advancing. Each lineage's ledger also carries a cumulative-drift line vs base, set BEFORE the lineage's first real run and never renegotiated after a bad result; crossing it stops the chain building on itself — the next run restarts from base or the last known-good version, and drifted versions stay archived, never deployed.
- **Rollback:** every verified version stays in the Sabrent archive (the swap rule), so if a degraded model ever reaches the library it is replaced by the last known-good version — and the incident is written into the failure ledger as a process failure, because the guard should have caught it first.

## Engines — use both, per job (Duckets, 2026-10-22)
"Do whatever is best": the program has TWO training engines and the run plan names which one a run uses and why.
- **mlx-lm-lora (MCP)** — the RSI loop driver for TEXT work: SFT/LoRA chains, preference modes, fast iteration on the small roster. Text-only modes.
- **Unsloth (Studio, on the Mac)** — trains VISION (its vision fine-tuning is the route for image+text jobs, e.g. CannaAI photo diagnostics) and any job where it is plainly the better tool. Driven with the unsloth-manager skill's tooling and the same discipline learned on Bolt (guarded launchers, verify by progress lines, never by a route return).
- **Same gates on both engines:** window + 10 AM done, ≤35B ceiling, written run plan, curation, Sabrent RSI-tree backup before training, chunking to fit, eval vs parent (incl. failure cases), verified LM Studio deployment + swap, lineage labels. An engine route that isn't proven for a target yet gets a prep/smoke night that proves it — never a hopeful full run.
- **Unsloth-the-tool ≠ Bolt-the-run.** Bolt stays parked (Duckets, 2026-10-22) unless RSI proves out and he reopens it. Using Unsloth for small roster models does not resume Bolt.

## Pre-run RAM & load management (Duckets, 2026-10-22 — "this is why we have training mode")
No training run starts on a loaded machine. Before ANY run, on either engine:
1. **Measure honestly:** `lms ps` + real RSS totals (never `memory_pressure` free % — it counts purgeable cache and lied before the 2026-10-20 crash). Know exactly what's loaded and what it's costing.
2. **Wait for quiet first:** nothing starts while anything is GENERATING (Hermes brain jobs have right of way at their times; re-check to 04:00, then it's a prep night).
3. **Free the machine — training-mode discipline:** once quiet, unload loaded LM Studio models that tonight's run and tonight's remaining scheduled jobs don't need (`lms unload`), and clear non-essential user apps/processes the way the training-mode skill does — this is what training mode exists for.
4. **Lifelines NEVER get touched:** Muse.app, LM Studio itself, Terminal, SSH, Tailscale, the Hermes gateway, AVG, and all system processes stay up. Unloading a model is fine; killing a lifeline is not, ever.
5. **Still short → no run.** If headroom isn't genuinely there after cleanup, the night becomes prep. Forcing a run into a loaded machine is how loaded model sets get evicted and runs get jetsam-killed — both already happened once in this fleet's history.

## Rotation
Nights rotate through roster targets in order; a target with no prepared dataset/eval gets a prep night instead of a run night, then the rotation advances. First scheduled night is a **smoke night**: tiny run end-to-end (validate → train a few steps → status/log → eval harness check) to prove the pipeline before any real run.

## Preparation nights — non-training nights are work nights (Duckets, 2026-10-22)
"If it's not a training night you need to work on preparation while I'm asleep — make sure you're fully prepared for each training session day." Non-training nights (Mon/Wed/Fri/Sun) are PREP nights, owned by the same discipline as training nights: while Duckets sleeps, the next training day gets made ready and the program's build backlog gets worked. A prep night is never an idle night.
- **The readiness standard:** when a Tue/Thu/Sat window opens, that night's run is EXECUTE-ONLY — the run plan is complete (all fields, no blanks), the dataset is curated + privacy-screened + decontaminated + backed up and verified, the eval/selection sets exist, `check_training_config` has passed on the real config, and the machine-side facts (model artifacts present, disk, throughput current) are confirmed. If any piece is missing at window-open, the preparation failed earlier — the training-night prep fallback is the safety net, not the plan.
- **The standing prep queue** lives in `<repo>/templates/rotation.md` (Prep queue section) and is worked in order on every prep night, alongside that night's benchmark duties: next training day's full preparation first, then the build backlog (frozen suite incl. safety domain, scorer tool, decontamination tooling, selection/confirmation set construction, load proofs, dataset builds, drift-line proposals for Duckets' ratification, external-anchor baselines). Prep nights update the queue and the readiness line as they go.
- **Juno + Hermes work together (Duckets' standing order):** Hermes owns the machine-side prep — he lives on the Mac: dataset staging and curation runs, tool builds, load proofs, skill distillation (his own source family), machine/disk/model state, and a sanity check of every run plan against the real machine. Juno owns the program-side prep — run plans, ledgers, curation review (including the manifest-eyeball rule on Hermes' curations), benchmarks, verification, and the readiness call. **Each cross-checks the other:** Hermes' curated sets don't train until Juno has reviewed the manifest; Juno's plans don't execute until Hermes has confirmed the machine side. They coordinate through the shared files (rotation state, ledgers, manifests on the Mac) and Hermes' briefing channel — neither waits idle for the other, and a disagreement neither can resolve from the documents goes into the morning report as a question for Duckets, with the safer option taken in the meantime.
- **Deliverable:** every prep night leaves the rotation state showing (a) readiness for the next training day: READY or the named blockers, and (b) what backlog items advanced. Blockers that need Duckets (a download approval, a drift-line value, a job pick) are surfaced in the morning report, once, clearly — never as midnight questions.

## The fresh challenger — anti-degradation control (added by Duckets 2026-10-22)
Duckets' worry, in his words: "eventual degradation of other areas and loss of general skills and other skills over time." Lineage (training on top of old runs) is the main line — it's the only scheme that fits chunked multi-night datasets and compounds gains inside the window — but no chain compounds forever on faith. The frozen suite detects drift; the challenger CORRECTS it, empirically:
- **Triggers** (any one fires a challenger sequence for that chain): (a) two consecutive gate losses; (b) cumulative drift vs base reaches **half** the lineage's drift line (the line itself remains the hard stop); (c) every 4th kept version (v4, v8, …) regardless of how healthy the chain looks.
- **What it is:** a FRESH candidate trained from the BASE model on the chain's accumulated curated data (every chunk the chain has consumed, in order — the versioned Sabrent backups make this reproducible), with the replay slice included. It's a planned sequence like any real run (written run plan; sized across nights if the accumulated data needs it) — never an improvised marathon.
- **The face-off:** challenger vs chain head on the FULL gate — target eval, frozen regression suite, and GPQA (in-window or via the next benchmark night). The winner becomes the chain's current version: a winning challenger takes the next version number with a "fresh-restart" note in the ledger (its parent recorded as base + the face-off numbers); a losing challenger is discarded with its numbers logged, and the chain continues — now with measured proof that compounding is still earning its keep.
- **Either outcome is a deliverable:** the comparison (chain head vs fresh, all scores) is recorded in the lineage ledger and the morning report. Over time these face-offs ARE the program's evidence about when lineage helps and when it hurts — per model, not by ideology.

## Experience-driven improvement — failures AND successes (added by Duckets 2026-10-22)
Improvement targets what the fleet ACTUALLY does — what it gets wrong AND what it verifiably gets right — not just what the corpora happen to contain. Hermes' experience, the models' results, and Juno's experience are all training signal. **Hermes is a first-class source, not a bystander:** his session and decision history, his fixes, his prep-night distillations, and his brain-job lessons feed this loop the same way Juno's chat-side record does (personal content stripped per the privacy rule, always). Hermes' failures, the models' failures, and Juno's failures are training signal:
- **Failure ledger:** an append-only log at `<training-home>/failures.jsonl` on the Mac. Every notable failure gets a line: date, source (hermes / model name / juno), category (reasoning, tool-use, vision, instruction-following, factual, format, config), what happened, and what correct behavior would have been. Hermes appends its own and the models' failures as it sees them; Juno appends from the chat side. Duckets' corrections in any channel are failures by definition — log them.
- **Distillation (prep work):** ledger entries become (a) **eval cases** — the gate's hardest tests, held out and never trained on, so a version must prove it fixed real failures without regressing; and (b) **training rows** — the same situations with the corrected behavior, curated and backed up like any other dataset (a per-target `failures` dataset under `datasets/rsi/`). Failure categories also steer the other datasets: a category with many failures gets more/better coverage in curation, and chunk planning weighs failure-derived rows first — fixing real weaknesses outranks generic volume.
- **Accounting:** each morning report names which failure categories tonight's run targeted and whether the eval failure-cases moved. A run that improves a benchmark but not the fleet's real failures is a partial win and gets reported as one.
- **Success ledger (the other half — added at Duckets' question, 2026-10-22):** an append-only log at `<training-home>/successes.jsonl` on the Mac, same discipline as the failure ledger: date, source (juno / hermes / duckets / model name + gate), category, what worked, and the PROOF (how the outcome was verified — on the thing itself: a device listing, a byte total, a log line, a benchmark in the real runtime). **Only VERIFIED successes are entries** — an unverified "win" is a rumor and stays out, the same never-guess standard as everything else. Hermes appends his wins as he sees them; Juno appends from the chat side; every eval-gate pass and verified deployment is recorded as a model success.
- **Mining successes (prep work):** ledger entries become (a) **positive training rows** — verified-good behavior worth reinforcing: correct decisions, clean fixes, procedures that worked, distilled into the same curated datasets as everything else; and (b) **operator-corpus material** — the operator must learn what RIGHT looks like, not only what wrong looks like: successful decisions and executions are half its education. **Success rows are TRAIN-side only, never eval** — eval stays hard (failure cases + the frozen suite); a model is never graded on its own highlight reel.
- **Experience units — ledger schema upgrade (AgentEvolver import, 2026-10-22):** distilled ledger entries become retrievable **experience units** with two fields: **"when to use"** — the situation/trigger the entry applies to, which doubles as its retrieval key — and **"content"** — the strategy or precaution itself. Distillation sources include **comparative pairs**: a success and a failure on the same task type, mined together, teach the contrast neither entry teaches alone. Every unit passes a validation check before it can seed training rows (the verified-only rule, generalized from successes to all distilled material). And one no-training lever: for the operator track, retrieving the relevant units into the operator's context at inference time is free capability (their injection tests gained ~5–7 points with zero training) — retrieval ships before any operator weights do.

## Benchmarks — the external yardstick (added by Duckets 2026-10-22)
Internal evals say whether a version beat its parent on OUR data. Standard benchmarks say whether it actually got smarter by the yardsticks everyone else uses — the metric that decides, over time, what's worth keeping and what's worth removing.
- **Battery v3 — one benchmark per capability area, sequenced by signal-per-hour at 1–12B** (v1 was GPQA alone; v2 ordered broad coverage; the 2026-10-22 research pass re-ranked it — full verdicts in the goal's research notes). **Rollout order:** (1) **IFEval** (instruction following — best determinism, most SFT-sensitive) + **GSM8K** (math floor) + **ARC-Challenge** (cheap canary: a >3–5 pt drop is a smoke alarm, not a thermometer) + **MMLU canary** (a fixed stratified ~2,000-item loglikelihood subset run often; full MMLU on benchmark nights) in ONE harness, plus a **private perturbed GSM-style clone** as the contamination tripwire (public GSM8K is provably contaminated — GSM1k showed drops up to 13%); (2) **full MMLU** + **HumanEval+ / MBPP+** (coding; HumanEval+ n=164 → CI ±7.5 pts, greedy pass@1 only for gating; MBPP+ gives the small-tier floor); (3) **MATH-500**, stratified by level (L1–2 carry the signal at 1–3B), pinned token cap/parser, averaged runs; (4) **BFCL pinned subset** (~1,000–1,400 items; version AND FC-vs-prompt mode pinned to the actual LM Studio serving stack; per-category reporting, never just the overall); (5) **GPQA Diamond** — DEMOTED to evidence: at 1–12B most models sit near the 25% floor and n=198 carries CI ±6.6 pts, the weakest signal per hour in the battery (harness on hand: `~/workspace/bench/official/gpqa_diamond_parallel.py`; DuckBot 35B reference 111/198 = 56.1%, 2026-10-08 — a 35B-tier instrument). **TruthfulQA is NOT a gate** (wrong construct — imitative-falsehood trivia, not generated-hallucination drift; MC2-only diagnostic at most): the truthfulness slot is an **own-domain factuality probe** (fleet facts, scored against records), with HaluEval-QA/PopQA as candidates. **IFBench** joins as a quarterly audit (IFEval saturates/template-overfits even at 2B). **Vision:** the gate is **MMBench/SEED-Bench + POPE** (+ ChartQA/DocVQA if document work matters); **MMMU-val is quarterly evidence only** (900 scoreable items, near-floor and perception-dominated at this scale, costliest per item).
- **Tier rule:** a benchmark counts for a model only if the BASE scores meaningfully above that benchmark's floor. Floor status is recorded in the ledger; a floored benchmark reports "no signal," never a zero to beat.
- **Milestone veto (research amendment):** benchmarks are evidence under the nightly gates — but at chain milestones (kept-version multiples of 4, challenger face-offs), the FULL runs (full MMLU, BFCL full, safety suite) carry a pre-declared veto: a milestone score below the lineage's recorded floor for that benchmark blocks deployment pending Duckets' review. Purely passive evidence would be decorative.
- **External anchor (research amendment):** benchmark nights periodically score the best current open model of the same size class — a lineage anchored to an obsolete base accumulates opportunity cost no internal comparison can detect.
- The battery may split across consecutive benchmark nights per model; partial records are valid — every result lands in `<repo>/state/benchmarks/` and the ledger as it completes. One timed pilot per benchmark replaces runtime estimates before they're used for scheduling.
- **Protocol:** same harness, same settings, same model-serving conditions every run — a score is only comparable to scores from the identical battery version. **Precision parity (Duckets, 2026-10-23):** comparisons are only valid at matched precision — a candidate is fused/quantized to the same precision as the artifact it is compared against before scoring (the da7d lesson: a bf16 fusion compared against a Q4 base measures quantization, not training). The **context/scaffold template is pinned per benchmark family and recorded in the eval manifest** (AgentEvolver import, 2026-10-22): on identical weights their context-template comparison spread results from 0.506 to 0.720 — scaffold drift between versions would confound every comparison we make. Results (raw JSONL + score) are stored under the goal's `<repo>/state/benchmarks/` and the headline score is transcribed into the model's lineage ledger next to its eval numbers. Benchmark items are **eval-only, forever**: they never enter any training set, and curation never sources from benchmark files.
- **When:** on **non-training nights** (Mon/Wed/Fri/Sun, same 01:00–10:00 discipline, driven by cron `rsi-benchmark-nights`) as preparation work — baselines for roster bases and current versions, and scores for newly kept versions that didn't get benchmarked in their training window. Benchmark nights never train, never curate training data from benchmarks, and stand down entirely if a training/smoke job owns the night.
- **Machine discipline:** benchmarking loads models in LM Studio — record the loaded set first, load only the target, and restore the previous loaded set afterward. Never unload a model a live session is using; Hermes brain jobs keep right of way.
- **Role in decisions:** benchmarks are EVIDENCE layered under the hard gates (target eval + frozen suite decide keep/discard on the night). Every kept version gets a benchmark record; a headline-benchmark crater vs parent is a regression signal that triggers the keep/remove review (see Dataset curation §6) and is reported, never silently passed over. If the battery proves stable, Duckets may promote it to a hard gate — not before.
- **WINNERS-ONLY LINEAGE (Duckets, 2026-10-23 18:23):** "only winning models get trained on — if we hit one that is weaker on benchmark than the others we remove that one, document the failure and learn from that." PROMOTED by the owner: the benchmark record (one run per new model, bench nights) is now a removal criterion, not just evidence. A version whose record comes back weaker than its parent's / the chain's other versions — beyond noise (score the parent twice if unsure, per the tier rule) — is REMOVED: moved to the Sabrent archive per the swap rule (never hard-deleted; the base always stays), struck as a lineage parent, and the chain head reverts to the last winning version. The failure is DOCUMENTED (lineage ledger entry with the numbers + a `failures.jsonl` entry) and LEARNED FROM (the failure distills into eval cases + corrected rows like every other failure — that is what the failure-mining loop is for). Only winning models are ever trained on: a removed or benchmark-weak version is never a parent, never a fallback, never quietly retried as-is.

## Skill libraries as training data (added by Duckets 2026-10-22)
Both agents' skill libraries are training data — they are the fleet's written-down competence: verified procedures, hard-won lessons, tool discipline, gotchas. Juno's skills (system + custom, including this program's own) and Hermes' skills (his mlops set and everything else he maintains) distill into: (a) **procedural SFT rows** — task → the procedure that works; (b) **scenario rows** — a situation → applying the right skill's method; (c) **eval cases** — does the candidate follow the procedure correctly (held out, like all eval).
- **Hermes is self-improving — that buys the program four things (Duckets, 2026-10-22):** (1) a **living corpus**: Hermes keeps writing and improving his own skills, so this source refreshes and rises in quality on its own — as Hermes gets better, the data distilled from him gets better, and models trained on it feed back into the fleet that helps him (the operator track most directly); (2) **improvement trajectories**: his skill REVISIONS are before/after pairs — what changed and why is exactly the shape of learning-to-improve data, the same family as failure→correction rows; (3) **prep labor at the source**: Hermes lives on the training machine and is awake overnight anyway — he distills his own skills and mines his own sessions locally on prep nights, no transfers, no Juno bottleneck; (4) a **teacher who improves**: his generated material (synthetic rows, distillations, reflections) gets better as he does, compounding the teacher-generated source family too.
- **Discipline (same as every source):** snapshot the skill libraries per curation and record the snapshot in the manifest (never train on a moving target); privacy screen applies with extra care — skills carry machine paths and operational details, so generalize (paths → placeholders) or drop; quality filter prefers skills tied to verified outcomes (cross-reference the success ledger) over stale or speculative ones; a skill that contradicts the current verified record is a failure-ledger entry, not training data.

## Research amendments — what the evidence changed (2026-10-22)
A sourced research pass over continual fine-tuning practice (full report in the goal's research notes) found 18 gaps; the ones not already fixed inside the sections above are law here:
- **Selection vs confirmation sets.** The nightly gate scores on the SELECTION set. A separate CONFIRMATION set is touched only at milestones and challenger face-offs — a set consulted every night becomes a validation set and every reported gain inflates (adaptive overfitting). Both rotate quarterly; the lineage ledger logs how many candidates were tried against each set (the search denominator). Inside a run: at most **3 pre-declared checkpoints**, selected on the selection set, confirmed once on the confirmation set — best-of-many checkpoint picking is the same curse in miniature.
- **Artifact truth (also settles the open C4 question).** Three artifacts get scored: the adapter, the bf16-merged model, and the SERVING artifact (quantized, production template/settings). **The gate judges the serving artifact** — merging a LoRA into a 4-bit base measurably degrades it (perplexity back near the un-tuned base in published tests), and re-quantizing a quantized file compounds rounding error. The **bf16 merged master is always the lineage's source of truth and the next run's parent**; quantized serving copies are derived from it, never the other way round. Terminology corrected: LoRA-on-quantized is QLoRA-style, not QAT; chains that must merge repeatedly should prefer QA-LoRA-style adapters. ALL evals (gate, frozen suite, benchmarks) run through the production serving configuration — template, system prompt, sampling defaults, quantization — or they measure a model that never ships.
- **Safety is a regression axis.** Benign SFT alone erodes refusal behavior, and LoRA can strip refusals while capability suites pass. The frozen suite therefore includes a pinned **refusal + over-refusal set** (~100–200 prompts: things the base refuses that it should, and benign look-alikes it must NOT refuse), scored vs base every run, under its own per-domain floor.
- **Per-domain drift floors, not one aggregate line.** The drift line applies PER frozen-suite domain (instruction / reasoning / coding / tool use / conversation / safety), because one domain can collapse behind a green aggregate. Every run also records non-score drift signals: held-out general-text perplexity, output-length distribution, distinct-n, refusal rate.
- **Per-chunk probes.** The frozen suite carries a small probe set per trained chunk, so chunk-level forgetting (chunk k erasing chunk 1) is visible by name, not inferred.
- **Hyperparameter carry-over (per chain, written in the run plan):** LR **re-warms to a fraction of the prior peak and re-decays** each generation (never a fresh full cosine, never continuation at the decayed floor); **α = 2r** default; LoRA rank **non-increasing** as the chain lengthens; per-row **cumulative exposure counter** in the manifest — rows retire past ~4 total exposures (replay rows silently accumulate epochs across generations otherwise).
- **Chunking = stratified interleaves.** Big sources are chunked as representative slices of the WHOLE dataset each night, never topical blocks — topical chunking maximizes both forgetting and last-chunk recency privilege, and rigs the challenger comparison.
- **Challenger fairness.** A challenger run plan pre-declares its token/epoch budget and schedule; the face-off is judged on the CONFIRMATION set (the chain head was selected against the selection set — judging there rigs it for the incumbent).
- **Chain limits + plasticity.** Every lineage ledger pre-declares a **max chain length** (versions) that forces a refresh review (fresh challenger or re-base onto the best current base). At milestones, a **plasticity probe**: train a fixed probe chunk from the chain head and from base, compare achieved loss — a chain that can no longer learn is retired even if its scores still look fine.
- **Judge protocol.** Any judge-scored eval item: pinned judge model + prompt version, both-orders pairwise with only consistent wins counted, and a 50–100-item calibration set reviewed by Duckets, re-run whenever the judge changes. **Reference-anchored (AgentEvolver import, 2026-10-22):** where a reference answer or trace exists, the judge scores AGAINST it (coverage of the essential steps, functional equivalents count) with a hard zero for content unrelated to the task; the judge is always a frozen-tier model larger than the candidate — a lineage head never grades its own homework — and judge influence stays BOUNDED everywhere: their ablation showed a naive judge producing almost no improvement at any data quality, and heavy process-judge weight actively degrading long-run results (overfitting the judge's heuristics instead of the task). Outcome and execution evidence outrank judge scores wherever both exist.
- **PII erasure path.** Append-only backups and the privacy rule conflict the first time erasure is required, so: dataset backups are written under a per-version key and the backup manifest keeps a row index — erasure = crypto-shredding (destroy the version's key + delete its row index), recorded in the manifest. Building this into the backup tool is a prep-night task.

## Model potential & saturation — knowing when to stop (Duckets, 2026-10-22)
"We should also consider a model's max potential so we know when to stop training because it can't really improve past that point." Every lineage carries a **potential band** — an honest estimate of how far this base can go on our metrics — recorded in its ledger at chain start and revised at milestones:
- **Band references:** the base's own baseline scores (floor); the frozen teachers' scores on our target eval + frozen suite (a student rarely exceeds its teachers on their own turf); published best-known results for this base model; and the benchmark nights' external anchor (best current open model of the same size). The band is a range with named sources, never a single magic number, and it is Duckets-visible in the ledger. **Caution (AgentEvolver lesson, 2026-10-22):** published self-improvement numbers generally arrive without significance testing — treat any band top sourced from published figures as optimistic until our own battery confirms the neighborhood.
- **Headroom** = band top − current version, reported in the morning report as versions accumulate. A chain with wide headroom and shrinking gains has a data/method problem; a chain near its band top with shrinking gains is simply DONE.
- **Saturation — a chain is declared saturated when any of these hold:** (a) two consecutive KEPT versions each gain less than the gate margin on the target eval AND move the battery by less than run noise — improvement has flattened inside measurement error; (b) the chain head reaches ~90% of the band top on the primary metrics; (c) the milestone plasticity probe shows the chain head learning the probe chunk materially worse than base does (the capacity to improve is gone even if scores look fine). The gains-per-version series in the ledger is the primary evidence; no single flat night declares saturation.
- **What saturation means:** the chain STOPS — no more training nights, no challengers (a challenger answers "is compounding still helping," and saturation already answered it), no shame in it. The final version stays deployed as a worker; the model may still serve as a tier teacher/judge where it qualifies. The rotation slot goes to a fresher base or another chain with headroom. The ledger records the verdict + evidence + the final band. **Revisit only on new evidence:** a materially better dataset, method, or a new base generation — Duckets' call, proposed in a morning report, never assumed.
- Saturation is distinct from the drift stop (a chain getting WORSE) and from the max-chain-length review (a calendar backstop): saturation is the chain succeeding until it flattens at its ceiling.

## Imports — AgentEvolver (ModelScope / Tongyi Lab), mined 2026-10-22 at Duckets' order
AgentEvolver is a self-evolving agent system built on three mechanisms — self-questioning (exploration-driven task synthesis), self-navigating (a reusable experience pool), self-attributing (step-level credit assignment) — over an RL (GRPO) loop. **Platform verdict: methods only.** Its current stack is veRL + vLLM on CUDA (experiments on 8× A100-80GB); there is no MLX/Apple-Silicon path, so none of its code runs here. (This corrects our 2026-10-19 note, which named the older Megatron/SGLang stack.) The GRPO machinery — advantages, clipping, experience-mixed rollouts as a training dynamic — does not transfer to an SFT night; what transfers is its data, judging and experience engineering, wired into the sections above: feasibility-by-replay (curation §11), difficulty-parameterized synthesis + task schemas (§12), step attribution as row surgery + guidance stripping (§13), reference-anchored bounded judging (judge protocol), experience units + comparative pairs + inference-time retrieval (experience section), scaffold pinning (benchmark protocol), and the published-numbers caution (potential bands). Sources: github.com/modelscope/AgentEvolver; arXiv:2511.10395; CuES follow-up arXiv:2512.01311.
- **Lessons kept, beyond the wired rules:** (1) Task generation was their biggest single win — bigger than the RL refinements — which validates this program's prep-night/curation-first economics. (2) Their quantities saturate fast (~100 good tasks captured most of the gain) — expect band ceilings sooner than intuition says. (3) **No multi-generation evidence exists there either:** every published run evolves once from a fixed base; nobody has shown merge → retrain chains compounding across generations. Our lineage question stays open, so the challenger triggers and drift floors stay conservative. (4) Pipeline sub-components are load-bearing: removing one quiet piece (their selective boosting) dropped the system BELOW its plain baseline — ablate before removing anything from our curation pipeline. (5) Narrow training can actively harm off-domain work (their 7B regressed below zero-shot cross-domain) — one more independent vote for per-domain frozen-suite floors over aggregate scores.
